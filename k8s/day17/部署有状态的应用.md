## statefulset数据持久化：

#### 2.1、k8s数据持久化介绍

```
kubernetes 集群中不会为我们处理数据的存储，我们可以为数据库挂载一个磁盘来确保数据的安全。你可以选择云存储、本地磁盘、NFS。
本地磁盘：可以挂载某个节点上的目录，但是节点挂掉后服务没法访问
云存储：不限定节点，不受集群影响，安全稳定；需要云服务商提供，裸机集群是没有的。
NFS（ 网络文件系统 ）：不限定节点，不受集群影响
```

#### 2.2、statefulset使用本地磁盘数据持久化（官方不推荐使用）：

> 把节点上的一个目录挂载到 Pod，但是已经不推荐使用了，文档配置方式简单，需要手动指定 Pod 跑在某个固定的节点。仅供==**单节点测试使用**==；不适用于多节点集群。
>
> hostPath.yaml
>
> 类似于docker中的bind mount挂载方式。

```
vi mongo.yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mongodb
  namespace: test
spec:
  replicas: 1
  selector:
    matchLabels:
      app: mongodb
  serviceName: mongodb #必须
  template:
    metadata:
      labels:
        app: mongodb
    spec:
      containers:
      - name: mongo
        image: mongo:4.4
        volumeMounts:
        - mountPath: /data/db # （pod）容器里面的挂载路径
          name: mongo-data # 卷名字，必须跟下面定义的名字一致
      volumes:
      - name: mongo-data # 卷名字
        hostPath:
          path: /data/mongo-data # 节点上的路径 (服务器的路径)
          type: DirectoryOrCreate # 指向一个目录，不存在时自动创建
---
apiVersion: v1
kind: Service
metadata:
  name: mongodb
  namespace: test
spec:
  selector:
    app: mongodb
  type: ClusterIP
  # HeadLess
  clusterIP: None
  ports:
  - port: 27017
    targetPort: 27017
测试：
部署apply后进入数据库中添加数据
kubectl delete -f mongo.yaml
当在其部署时数据依然存在
```

## ✅ 原因：动态供给（Dynamic Provisioning）

在案例2中，你定义了：

```
storageClassName: mongo-sc
```

只要这个 `StorageClass` 背后有 **provisioner（存储插件）**，Kubernetes 就会自动帮你做这件事：

👉 自动流程：

1. StatefulSet 创建 Pod
2. 根据 `volumeClaimTemplates` 创建 PVC（3个）
3. **StorageClass 自动创建对应 PV（3个）**
4. PVC 自动绑定 PV

👉 你只写 PVC，PV 是系统帮你生成的

------

## 📌 对比一下两种模式

| 方式              | 是否需要手动创建 PV | 说明              |
| ----------------- | ------------------- | ----------------- |
| 静态供给（案例1） | ✅ 需要              | 你自己提前建好 PV |
| 动态供给（案例2） | ❌ 不需要            | 系统自动创建 PV   |

------

## ⚠️ 但有一个重要前提

👉 **StorageClass 必须有有效的 provisioner**

比如常见的：

- 云环境：
  - AWS EBS
  - GCE PD
- 本地：
  - NFS provisioner
  - local-path-provisioner（k3s默认）

------

## ❗你案例里的这个配置要注意

你写的是：

```
provisioner: kubernetes.io/no-provisioner
```

👉 这个其实表示：

❌ **不会自动创建 PV！**

👉 这种情况下你仍然需要：

- 手动创建 PV（类似案例1）

------

## 🧠 结论（重点记住）

### ✅ 真正“自动创建 PV”的写法应该是：

```
provisioner: ebs.csi.aws.com   # AWS 示例
```

或者（本地常见）：

```
provisioner: rancher.io/local-path
```

------

## 🎯 一句话总结

👉 **是否需要手动创建 PV，取决于 StorageClass 的 provisioner：**

- 有 provisioner 👉 ❌ 不用建 PV（自动）
- no-provisioner 👉 ✅ 必须手动建 PV
